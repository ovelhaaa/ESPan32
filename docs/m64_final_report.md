## 8. Performance regression (Phase P) and hardware smoke (Phase R)

No performance optimization was reopened. An objective hardware smoke was run
on the ESP32-S3 (COM10). Evidence: `docs/hardware/m64_smoke_summary.md`,
`docs/hardware/m64_production_boot.log`, `docs/hardware/m64_active_smoke.log`.

```text
production boot (22 s):    deadline 0, I2S 0/0/0, heap delta 0, BLE connected
active musical soak (210 s, PAN+BELL, 82,686 callbacks, 1,197 MIDI events):
    nominal overruns 31, max callback 3,079 us, max streak 1, max debt 412 us
    I2S timeout/short/TX 0/0/0, MIDI drops 0, BLE reconnects 0, crash 0, heap delta 0
```

Every overrun was isolated and fully recovered; this is not a reopen condition.
The soak monitor's `FAIL` is the superseded strict `deadline == 0` gate; the
accepted buffered high-energy behavior is defined by the performance contract.
The only unassessed item is *audible* glitch/dropout, which requires a human on
the DAC/headphone chain.

## 10. Known limitation (frozen)

See [performance_contract_v1.md](performance_contract_v1.md) section 7. Extreme
high-energy 8-voice Bell safety saturation can exceed the nominal block period
for consecutive callbacks; the 6x128-frame I2S pipeline absorbed it with
bounded debt and zero transport failure.
